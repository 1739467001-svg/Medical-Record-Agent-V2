## 一、文档定位

本文回答一个问题：**这套系统以什么形态交到东阿县人民医院手里，医院怎么用起来。**

系统定位先讲清楚：这是一个**病历书写辅助工具**——医生问诊录音（可说方言），系统转写并起草病历草稿，医生逐字段核对修改、签名归档。AI 只打草稿，**病历的责任主体始终是签名的医师**；无依据的内容一律留空警示（黄色待补，质控强制拦截），绝不臆造。

| 维度 | 现状 |

| 工程进度 | 31 项任务已交付（M1 / M1.5 / M2.0 完成），git 工作树干净，已推 GitHub |
| 数据资产 | 6 位真实患者（12 人次住院、187 份病案文书全文）、6 组真实医患音频，全部来自院内真实导出，**系统零编造数据** |
| 质量基线 | 金标准评测（以医生真实病历为标准答案）：入院记录可用率 73%、实体召回 95%/精确 95%（规则引擎基线，接入真实大模型后同口径复测提升） |
| 待外部条件 | ① ASR 语音引擎 Key（讯飞 WS 通道已按官方协议实现完毕）；② 大模型 API 方案（接入骨架就绪，失败自动回落）；③ HIS 接口文档（数据源 Provider 骨架就绪） |

**一句话状态：功能与工程已就绪到"试点可用"水平，三条外部条件到位即可在 30 分钟内挂接真实引擎，进入真实使用与数据积累。**

## 三、交付形态总览（三级形态，对应三个阶段）

### 形态一：源码资产交付（已就绪）

- 私有 GitHub 仓库：`github.com/1739467001-svg/Medical-Record-Agent-V2`（main 分支，与研发进度同步）；
- 交付内容：全部前后端源码、数据构建脚本、部署套件、四份手册、187 份病案数据层；
- 意义：医院（或后续任何承建方）**永久持有完整源码与技术资产**，不存在被单一供应商锁死的问题。

### 形态二：云端试用环境（已就绪）

- 已部署至研发方云服务器，与仓库功能完全同步，可远程访问；
- 用途：院方领导、科室主任**不动任何院内设备**即可体验全流程（建议开启脱敏开关）；
- 边界：试用环境仅用于体验与决策，**不承载正式患者数据**；正式使用必须转入形态三。

### 形态三：院内私有化部署（正式交付形态）

系统部署在医院自己的服务器上，运行于院内局域网，患者数据不出院。这是面向医院的最终形态，技术方案见第四章。

> 三种形态不是三选一，而是**递进关系**：云端试用 → 院方决策 → 院内试点 → 全院推广。当前已走到第二级。

## 四、院内私有化部署技术方案

系统刻意做了"低基建门槛"设计，三条部署路径按医院条件任选（`deploy/` 目录全部现成）：

| 路径 | 适用 | 要点 |
|---|---|---|
| A · Docker | 医院有容器环境 | `docker compose up -d` 一条命令拉起，数据卷持久化，跨服务器迁移最省事 |
| B · systemd 裸机 | 院内普通 Linux 服务器（推荐） | 拷贝目录 + 两个 systemd 命令即上线；服务单元内置安全加固 |
| C · nginx + TLS | 需公网/域名访问时 | TLS 终结 + IP 白名单/基础认证示例（公网必须 HTTPS，否则浏览器不给麦克风权限） |

关键工程特性（均已实测）：

- **零依赖运行**：BFF 为纯 Python 标准库实现，信息科**无需安装任何包、无需联网下载依赖**——这是为院内网络环境专门做的设计；
- **数据库**：默认 MySQL（信息科已有实例可直接复用，驱动 pymysql 已随项目打包，无需安装）；配套幂等迁移与定时备份脚本（含 crontab 方案）；另保留 SQLite 测试后端（显式环境变量启用）；
- **服务器规格**：试点 2C4G/40G 即足够；**无 GPU 要求**（大模型走云端 API 时）；
- **上线检查单**：8 项逐条勾验（健康检查、持久化、麦克风权限、备份、自检全绿、脱敏）。

## 七、安全与合规姿态

1. **数据不出院**：正式形态下，患者数据（录音、转写、草稿、归档）全程留在院内服务器；
2. **云端引擎的数据边界需确认**：ASR 转写与大模型生成如走云端 API，语音/文本会经过引擎厂商服务器。**这是唯一需要院方正式确认的合规点**，选项：a）接受厂商医疗云合规条款（各家均有医疗行业方案）；b）数据脱敏后上云；c）二期医院 GPU 私有化后彻底内网闭环（方案 4.3.3 已规划）；
3. **密钥安全**：所有引擎密钥仅存服务器 `config.json`（0600 权限），浏览器与日志中不出现明文，对外演示自动脱敏；
4. **全程留痕**：登录/录音/生成/修改/留空/签名归档每一步写入数据库（SQLite WAL 断电安全 / MySQL），满足医疗审计追溯要求；
5. **AI 责任边界**：系统不做诊断决策，只做书写辅助；黄色缺失项质控强制医生处理；签名即医师对内容负责。建议与医务科确认此定位表述（辅助书写工具，非临床决策支持）；
6. **建议的正式合规动作**（试点后期）：信息系统等级保护定级备案（建议等保二级起）、数据安全自查（按《数据安全法》《个人信息保护法》）、与 ASR/大模型厂商签署数据处理协议。

## 十、验收口径（沿用规划方案 6.2 并工程化）

1. **功能验收**：上线检查单 8 项全绿 + 三类文书全流程跑通无阻断；
2. **质量验收**：金标准评测报告（覆盖率/相似度/可用率/实体召回）达到阶段目标；评测口径全程可复现（同一案例重复运行结果一致）；
3. **安全验收**：密钥明文零暴露检查、留痕完整性抽查（抽 10 条归档核对审计链）、脱敏开关验证；
4. **联调验收**（阶段 3）：金标准案例回填 HIS 准确无误、归档号对应关系可追溯。
